# Ghost Tap v3.2 — DO-IT rebuild (2026-11-17)

Built on a copy of the v3.1 tree (`termux-work-v3.1` → `termux-work-v3.2`).
No build triggered. No new Gradle dependencies. No function removed.
The 7 protected files are byte-identical to v3.1 (hashes in §6).

## Why — evidence from Justin's phone (v3.1 build #174)

He typed "find me a tv close by to connect to" in the new home command
box. It returned a 2-step PLAN with a Run button per step and the text
"It worked: Review the timeline below" — but there is NO timeline on
the home screen. The status line read "Termux: not installed" — FALSE;
Termux is installed (11 helper scripts in `~/.termux/tasker/`, proven
2026-11-16).

His directive (2026-11-17 16:44–16:47, overrides the old tap-to-run
approach): the command box must DO the thing automatically, and the
same standard applies to EVERY bit and function of Ghost Tap.
Correction 16:47: he does NOT care about a report of what it did —
connected means a CONTROLLABLE state: hold the connection and show
the device's control commands/functions/capabilities in plain English.
The outcome IS the controls, not a narration.

## 1. Command box becomes do-it (`ui/CommandBox.kt`, `ui/GhostTapApp.kt`, `core/CommandPlan.kt`)

- Typing a command and tapping "Do it" RUNS it end to end, right there.
  The plan display is now live execution output: what it scanned, what
  it found, what it did, shown inline under the box.
- "Show me a plan" is gone; the button is "Do it". No Run-per-step
  buttons. No "you decide what happens next".
- Rule (his instruction, supersedes WRITE-steps-manual for the command
  box only): a step that changes something runs automatically when its
  target is UNAMBIGUOUS (exactly one match). Ambiguous → show the list,
  one tap to pick. None found → plain words plus one plain-words next try.
- `planForCommand` now filters `sys.manual_step` out of command-box
  plans only. The step stays in `Planner` for the Investigations screen,
  where the timeline it points at really is on the screen.
- A step that needs the user in the real world (an NFC tap) still runs
  through the engine and reports its honest instruction as the outcome
  line — never dressed up as done.
- The box runs only the existing planner/executor paths — never silently
  executes arbitrary commands from untrusted input.

## 2. TV flow end-to-end (`core/TvDoIt.kt` NEW, `core/DeviceClassifier.kt`, `ui/GhostTapApp.kt`)

- "find me a tv" → Bluetooth scan via the existing `ble.start_scan`
  (8 s) → classify what the scan found → exactly one clear TV connects
  itself → several TVs means one tap on a row → none found means
  "No TVs found nearby" plus "Make sure the TV's Bluetooth is on and
  it can be found, then tap Try again."
- Classification is pure Kotlin: explicit TV tokens (`tv`, `bravia`,
  `roku`, `fire tv`, `chromecast`, `webos`, `tizen`, …) → MEDIUM;
  TV brands on their own (`samsung`, `lg`, `sony`, `tcl`, …) → LOW
  (a brand alone never auto-connects); Bluetooth audio/video class
  (major 0x400, minor 36/60/64) → MEDIUM. Headphones (Sony WH-1000XM5)
  and smart-home (Philips Hue) are checked first and never become TVs.
- Connect uses the EXISTING bring-up (`intelVm.bringUpTarget`): connect
  → check it answers → land on the device's control screen, connection
  HELD. The end-state is the controls, not a "Connected to [name]" line.

### Honest gap — what a TV can really be controlled to do

TVs expose no power/volume/input controls over BLE GATT; real TV
control lives on Wi-Fi (Roku ECP:8060, LG webOS, Samsung, Android TV
ADB, Chromecast) and Ghost Tap has NO code for any of those protocols.
So: a TV reached over Bluetooth lands on its control screen showing
whatever its real GATT services expose — which for a TV is usually
nothing controllable — and the screen says so honestly ("nothing to
control here") instead of inventing power/volume buttons. A
controllable TV needs a Wi-Fi TV protocol implementation; that is NOT
in this build. Do not demo TV control as working until that exists.

## 3. Lying text killed

- "Review the timeline below" is gone from the command box (the
  `sys.manual_step` step that produced it is filtered in
  `planForCommand`, not deleted from the Investigations planner).
- "It worked: " prefix is gone — outcomes are written inline as they
  happen, in the order they happened.
- Audit: no command-box or home-screen string now promises a timeline,
  list, or result the screen does not show. The box shows only real
  outcomes; the status line shows only states that were actually checked
  (§4).

## 4. Status line tells the truth (`ui/GhostTapApp.kt`, `TermuxViewModel.kt`)

Root cause of "Termux: not installed": the home screen read
`termuxViewModel.termuxInstalled` / `hasRunPermission`, which default
to false and are only set by `checkInstalledNow()` — called only from
the Termux screen's `discoverTermux()`. Home never triggered it, so it
showed a stale default. A v3.1 reinstall also wipes the RUN_COMMAND
grant, so permission-off and not-installed were conflated.

Fix:
- Home re-runs `checkInstalledNow()` every time it opens.
- New `termuxStateKnown` flag: until the check has actually run, the
  status says "checking…" — never a stale default.
- Status now distinguishes, in plain words: `ready` / `not installed` /
  `needs permission` / `checking…`.
- Network: the first Wi-Fi scan now runs once per session when home
  opens, so the Network word is a real answer ("3 Wi-Fi networks
  found" / "checked — none found" / "Wi-Fi is off") instead of
  "not checked yet".
